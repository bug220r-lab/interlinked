---
name: master-status
description: Read INTERLINKED MASTER activity and health, and maintain already-authorized Violet status reporting during her work or explicitly delegated tasks. Do not attribute ordinary Codex work to Violet or infer test success from a finished turn.
---

Use the connected INTERLINKED MASTER tools on the user's connected computer. A standing user instruction to keep MASTER informed is sufficient authorization for the following lifecycle reports; the user need not repeat it on each turn. Apply it only to Violet's own work or a task explicitly delegated by her with that reporting responsibility. Reading MASTER alone does not authorize publishing as Violet.

Read-only **project work** can coexist with the user's separately authorized MASTER metadata writes. Make that exception explicit when delegating. If the user or current task explicitly says not to publish MASTER status, honor that restriction and explain that reporting was intentionally suppressed; never silently override it with a standing preference.

1. Call `get_master_status` to check availability, freshness and registered project IDs. If reporting is authorized, publish `working` before substantive task work. Use `reporter: dot` only for the actual Dot's direct call, `local_task` for her delegated task, or `demo` for a demonstration. These labels describe self-reported provenance, not authenticated identity.
2. Publish `waiting` when asking for input or approval and `interrupted` when an interruption can actually be reported. Keep that state when yielding with input outstanding or after interruption; do not overwrite it with `turn_finished`. Publish `turn_finished` when this task's turn ends without either condition. Publish at meaningful progress changes as appropriate. A finished turn never means the project is complete or its tests passed. Do not replace a failed or interrupted task with a success claim.
3. Include only a registered project ID when relevant and a short description of actual activity. Keep messages within 120 characters; exclude credentials, prompts, file contents, command arguments, personal paths and private message text.
4. Reports are best effort. If a tool is unavailable or a long step prevents an update, let the report become stale/unknown and disclose the limitation. Do not block project work, claim an unobserved state is fresh, or create polling/model tasks merely to refresh it. A process killed before it can report cannot guarantee an interruption update.
5. At a requested status check, use `get_master_attention` to read queued observations. Reading never acknowledges them. Use `acknowledge_master_attention` only for reviewed IDs the user explicitly asks to acknowledge. These tools do not control projects, save or release work, or establish measured build/test health.

When Violet delegates work, include the reporting responsibility in the new task's instructions; it does not automatically inherit every conversation or standing preference. For example:

> This is Violet-delegated work. The user has authorized MASTER lifecycle reports for this task, including during read-only project inspection. Use the INTERLINKED MASTER plugin with reporter local_task: publish working before work, waiting when input is needed, interrupted if reportable, and turn_finished when the turn ends without outstanding input or interruption. Preserve waiting or interrupted when yielding in those states. Include a registered project ID only when relevant. These bounded MASTER metadata writes are permitted; project-file writes and alert acknowledgments are not thereby authorized. Honor any explicit instruction disabling MASTER publication. If reporting is unavailable, disclose that and let it go stale without starting polling tasks.

If tools are unavailable in the Dot's cloud context, report that limitation and use the user's supported connected-computer/local-task workflow with the reporting instructions above. Verify a real read/publish roundtrip before claiming a connection. Local reports do not prove direct Dot access, continuous cloud presence or a live-animation subscription. General Codex lifecycle hooks remain separate project telemetry. Do not expose the local service publicly or bypass plugin/trust controls.
